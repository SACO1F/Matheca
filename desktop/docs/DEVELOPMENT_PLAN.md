# Mathector Windows 后续开发计划

更新日期：2026-10-15。依据：当前桌面源代码、最新 Windows x64 便携版及本次回归测试。配套结果见 [当前软件测试报告](CURRENT_TEST_REPORT.md)。

## 1. 开发方向

建议先完成一轮稳定性与质量收敛，再扩展新功能。接下来最值得投入的方向依次是：真实试卷识别质量、大题库性能、数据恢复与导出一致性、维护与发布流程，最后才是移动端互通。

这份计划以 Windows 桌面版为主。根目录 `docs/product-plan.md` 是 Android 规划，不能直接作为当前桌面版的功能状态表。桌面版仍标记为 0.1.0；Android 是另一套工程与版本。

本文中的周期与性能指标是建议目标，不是已实现能力或交付承诺。真实任务需在样本和目标机器确定后再估算。

| 领域     | 当前已有能力                                                           | 后续需要解决的问题                                       |

| 题集     | 三列布局、局部选题、排序、移除、校对往返、文档设置                     | 批量选题与排版预检、长题集效率                           |
| 导出     | PDF/Word、参考预览、图形/选项图片、按题型留白与手动留白                | 实际 Word/WPS 兼容性、超高题目分页、预览与最终文档的边界 |
| 数据     | SQLite、Windows ZIP 备份/合并恢复、当前操作撤销、业务历史              | 定期备份、崩溃恢复演练、容量与保留策略                   |
| 交互     | 固定图标栏、知识点侧边栏、悬浮树、过渡动画、减少动态效果               | 低性能机器与不同 DPI、浮动按钮遮挡检查、键盘回归         |
| 接口     | 用户自行配置、多模态请求、加密保存 Key、独立教程与简短说明             | 服务能力与错误分类、真实模型质量/成本记录                |

当前主要限制：单批最多 20 个输入文件；单文件图片/PDF 50MB；单 PDF 20 页；每题最多 6 张 PNG 图形，图形合计按编码长度限制为 8,000,000 字符；图形宽度自动或 20–160mm；任务同时执行上限 2。应在扩大限制前先测内存、耗时与失败恢复。

## 3. 技术分析

### 3.1 保留现有布局，先处理数据流

`src/renderer/masonry-cards.tsx` 保留 CSS Grid 行跨度、ResizeObserver 测高、requestAnimationFrame 合并更新和卡片位置/宽度动画。当前产品视觉上采用题目列表，不应为优化性能重新改回瀑布流或直接替换布局库。

侧边栏切换已经采用最终宽度一次落位，再移动工作区的方案；卡片展开仍保留独立的布局动画。进一步优化应先测事件处理、公式渲染、数据刷新和长帧来源，避免多个动画系统同时改变同一元素。

### 3.2 100 题分页不等于数据分页

`src/main/main.ts` 的 `library:state` 每次返回完整题目、题集、关系及任务；`src/main/store.ts` 的题目读取没有分页；`src/renderer/main.tsx` 在接收完整状态后再按 100 题切片。

这意味着显示分页降低了 DOM 数量，但没有降低数据库读取、JSON 解析、IPC 传输和前端筛选的全部成本。图片存为题目里的编码数据，进一步放大全量刷新负担。这是代码确认的扩展风险，不能直接等同于已经测得“大题库卡顿”。

### 3.3 文档预览与 Word 格式存在边界

`src/main/export.ts` 的预览统一由 PDF 渲染；Word 是另一个文档生成路径，当前公式以图片方式写入。Word 参考预览不能保证与实际 Word/WPS 分页完全相同，也不能宣称公式可原生编辑。

优先补足兼容测试与提示；原生 OMML 公式应作为独立增量任务，保留不支持公式的可读回退。

### 3.4 撤销与历史记录职责不同

`src/main/store.ts` 的删除、加入题集及确认校对撤销快照保存在内存中，只支持当前可操作的最近记录。历史记录用于追踪业务操作，并不是可回放的多步撤销栈。

短期保持当前交互约定，并明确重启后的边界；若后续需要多步恢复，应设计修订/回收站及容量策略，不能把现有历史列表直接当成恢复机制。

### 3.5 维护成本开始上升

主渲染组件约 3,236 行，主样式约 3,485 行。多个领域已经有独立组件，但导航、校对、筛选、题集和浮层状态仍集中在主文件中。现有 GUI 脚本数量多且缺少统一入口，本次也发现了过时定位。

推荐按领域逐步抽取，先建立回归保护，再移动代码。无需重写全部页面或引入新的状态库。

### 4.1 推荐性能验收目标

以下为待建立基准的建议目标，应先记录当前版本再冻结阈值：

- 题库数据集：1,000、5,000、10,000 题，分别测试纯文字/公式和含图片；明确图片体积与硬件。
- 本地筛选 P95 争取低于 300ms；初始可交互时间争取低于 2 秒。不把本次 100 题侧边栏数据外推到 10,000 题。
- 连续开关侧边栏 20 次、校对往返 20 次；最终宽度、选中题、滚动位置与原图位置正确，无 ResizeObserver 循环错误。
- 长帧同时记录数量和最长帧，不能只用总布局耗时判定“不卡”。
- 100%、125%、150%、200% DPI；正常窗口/最小窗口；减少动态效果；浮动加号与卡片底部操作不能遮挡。

### 4.2 识别基准建议

第一批建议 100–200 道人工核对题，至少覆盖文字题、复杂公式题、带图题、ABCD 图片选项、跨页题。样本需有使用授权；原卷、页码、题目边界与人工答案分开记录。

固定样本、服务、模型、提示词及测试日期，分别统计漏题/重复题/错拆题、条件与子题完整性、公式符号错误、图形关联错误、难度标签一致性、人工修正时间、失败率与费用。不把“接口返回成功”当作识别质量合格。

## 5. 分阶段执行建议

| 阶段          | 建议投入        | 工作范围                                             | 结束条件                                              |
| ------------- | --------------- | ---------------------------------------------------- | ----------------------------------------------------- |
| A：稳定性收敛 | 约 3–5 个工作日 | 文档同步、统一回归、异常恢复、DPI/浮层遮挡、长帧定位 | 核心套件稳定通过；有明确已知问题列表与发布记录        |
| B：主流程质量 | 约 1–2 周       | 真实识别基准、跨页/选项/图形问题、导出兼容样张       | 基准报告可重复；修复由真实样本驱动；PDF/Word 边界明确 |
| C：容量与维护 | 约 1–2 周       | 分页/增量状态、图片按需加载、索引、组件拆分          | 大题库实测改善；原有回归全部通过；无业务数据迁移损失  |
| D：跨端与增强 | 另行估算        | Android ZIP 协议、手机上传、原生 Word 公式、升级机制 | 完成目标设备与协议验证后再对外开放                    |

阶段可交叉推进，但新功能不能挤掉 A 阶段的数据安全和回归工作。真实服务、真机与办公软件环境未准备时，相关验收标记为待验证。

## 6. 文件清理与发布约定

已有 `scripts/clean-generated.ps1` 提供只读预览与手动执行入口。上轮实际删除被自动审批拒绝，没有完成清理。本计划不再次执行删除。

后续建立可配置保留策略：当前便携版、至少一份回退版、正在运行版本及必要证据保留；旧生成目录与测试数据先列出，再依规则处理。测试数据中可能包含输入文件副本和本地测试凭据，不应无限累积。

每次桌面生产代码修改后：适当检查 → `npm run make:portable` → 在独立 `MATHECTOR_TEST_DATA` 中启动新 EXE → 验证改动与核心回归 → 交付完整目录/EXE/ZIP/SHA256。不要终止用户正在运行的版本，锁定时使用新目录。

仅计划文档和测试脚本调整无需生成内容相同的新发布包，但测试报告必须明确被测包的实际路径与哈希。

## 7. 本轮不建议优先做的事项

- 再次大规模改变题库卡片或主导航布局。
- 未做大题库测量就替换 Grid、直接引入虚拟列表或新动画依赖。
- 同时引入云同步、账号、协作与手机实时上传。
- 未经基准校准就按 AI 难度评分自动确认校对。
- 用历史记录界面承诺任意步骤恢复，或用 PDF 参考预览承诺 Word 逐页一致。

建议下一轮从阶段 A 开始：先统一验证与当前文档，再依据测试数据处理剩余长帧、浮层遮挡和异常恢复。
